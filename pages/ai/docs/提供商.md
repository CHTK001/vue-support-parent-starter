## 二、拉取模型：OpenAI / CC / Gemini 三种协议怎么请求

「从提供商获取模型」只有一条实现：`fetchModelsFromUpstream` → `requestUpstreamModels`，
实际请求就是 `GET {base_url}/models`，认证头按供应商配置的 `auth_scheme` / `extra.auth_header` / `extra.auth_prefix` 决定（默认 `Authorization: Bearer <key>`）：

| 协议 | 请求地址 | 认证 | 覆盖行数 | 结论 |
| --- | --- | --- | --- | --- |
| OpenAI 兼容 | `{base}/models`；404 且非 Gemini 时补 `{base}/v1/models` 重试一次；Ollama 再回落 `/api/tags` | 默认 `Authorization: Bearer`，可改头名与前缀 | 213 | 支持 |
| Gemini | `{base}/models?key=<key>`（platform 含 google / gemini 时用查询参数认证） | `?key=` | 2 | 支持 |
| Anthropic(CC) | `{base}/models`（与其他协议同一条链，没有单独分支） | 只发一个认证头，**不带** `anthropic-version` | 1 | 看上游：CC 中转站（one-api / new-api 系）大多认 Bearer，能拉到；Anthropic 官方 `/v1/models` 要 `x-api-key` + `anthropic-version`，默认配置会 401（见第七节缺口） |

只有 **404** 会被当成「拉不到」，401 / 403 / 429 分别回「Key 无效」「没有读取模型列表的权限」「请求过于频繁」，页面据此区分「地址填错」和「Key 权限不对」。不拉模型列表的只有 4 类：ONNX（读本地模型门面）、路由组（读模型库成员）、免费渠道（读运行时合并路由表）、自填地址的 `custom`。

另有一条独立链路是「检测协议」（`probeProtocol` / `modelListCandidates`，探测某个地址支持哪些协议）：它按协议排一整串候选地址，Anthropic 发 `x-api-key` + `anthropic-version: 2023-06-01`，Gemini 用 `?key=`，OpenAI 试 `/v1/models`、`/models`、`/openai/v1/models`。那条链路是判断「地址支持什么」，不是这里的「拉模型清单」，两者别混。

## 五、限制与计费口径怎么同步（供应商详情「同步」）

入口：供应商详情 →「同步」→ `POST /api/providers/{id}/sync`。一次点击做五件事，结果按分节返回：

| 分节 | 数据来源 | 落点 | 拿不到时 |
| --- | --- | --- | --- |
| 限制 | 手动配置 → 官方文档登记表 → 上游响应头，按此顺序 | `sys_ai_provider.extra.provider_limits` | 页面显示「未收录」并列出已尝试链路，不写 0 |
| 计费标准 | 官方指标源（`ChatClientIndicators`）+ 上游 `/models` 的 pricing | `sys_ai_model_metrics` + 服务商模型行 | 已有价格不覆盖；官方源未接入时给出官方价格页 |
| 模型描述 | 上游 `/models` 的 `description` / `summary`；上游缺失时由公开目录补位 | `sys_ai_provider_model.description` | 默认只补空值，`overwrite_descriptions=true` 才覆盖（公开目录永远只补空值） |
| 公开目录 | models.dev 快照（`ProviderModelCatalogProvider` SPI，187 家 / 7568 个模型） | 说明补空；上下文 / 输出上限 / 多模态 / 思考 / 工具调用 / 附件 / 温度 / 权重等能力位补空；价格写 `sys_ai_model_metrics`（`source=models.dev`） | 未收录时保留上游与手工值；流式 / 异步目录不提供，返回 `null` 显示「未收录」 |
| 定价规则 | 点击同步时按 `ProviderPricingProvider.refresh` 实时抓官方价格页（当前 DeepSeek 已接入），静态 `provider-pricing-rules.json` 仅作离线兜底 | `sys_ai_model_metrics.sys_ai_model_metrics_pricing_rules`（JSON），并按 `model_pattern` 下发给模型行 `metrics.pricing_rules`；规则内带 `fetched_at` | 抓取/解析失败时不覆盖旧价，报告里回 `pricing_error`；未收录时为空，不拿标准目录价冒充峰谷价 |

**定价规则覆盖**：登记 1 家 / 11 条静态兜底，当前只有 DeepSeek 接入实时抓取并标 `verified=true`；其余厂商按同一 JSON 格式追加，不猜数值。DeepSeek 每次点「同步」都会重新抓官方价格页，页面改价后无需改代码，重新同步即落库；抓取失败会保留库里的上一次价格并在报告里给出原因。规则字段：

- `item` / `unit` / `quantity`：计价项与计价单位。`quantity=1000` + `unit=search` 表示「每 1000 次」，`quantity=10000` + `unit=char` 表示「每万字符」，`unit=hour` 表示按小时；
- `peak_price` / `off_peak_price` / `standard_price`：峰价、谷价、不分峰谷的标准价；`peak_windows` 写时区、星期与起止分钟（左闭右开），`off_peak_policy` 说明闲时规则；
- `model_pattern` 支持 `*` 通配；同一模型可同时命中标准 token 价与按次价，展示时分开列，不混算。

**「只有一个 appkey」的口径**：余额 / 用量只走同源 Bearer 接口；官方有 usage 接口的（OpenAI 兼容计费、DeepInfra、Together、OpenRouter、OpenCode Go 等）直接按 usage 折算，不要求另有余额端点。签到需要登录态，API Key 模板一律不适用；阿里云 BSS / 火山 / 百度 BCE / 七牛这 4 家 AK/SK 签名类不会自动出现在候选里（自动候选只取 Bearer 类预设）。

**限制机制**（`ProviderLimits`，与余额同构：一种机制一个实现，不逐家写死）：

- `manual`：读 `extra.limits_manual`，支持 `concurrency`、`requests_per_minute`、`requests_per_day`、`tokens_per_minute`、`tokens_per_day`、`monthly_request_quota`、`monthly_token_quota`、`billing_basis`、`currency`、`notes`、`source_url`、`model_concurrency`；
- `doc`：`ProviderLimitPresets` 从 datasearch 的 `provider-catalog/provider-limit-docs.json`（`ProviderLimitProvider` SPI）加载登记表（205 条），先按 provider id 精确匹配、再按主机名匹配；只有核对过原文的条目返回数值 / 计费口径，其余条目只回传 `doc_url`；
- `header`：复用本次 `GET /models` 的响应头，读 `x-ratelimit-*`（OpenAI 风格）、`ratelimit-policy` / `ratelimit-limit`（IETF 草案）、`anthropic-ratelimit-*`、`retry-after`。不额外发请求。

**扩展方式（SPI）**：新增机制不必改本模块 —— 声明 `ProviderLimitProvider` 的 Spring Bean，或在 `META-INF/services/` 登记实现即可；执行顺序由 `order()` 决定（内置 manual=10 / doc=20 / header=30），同一 `kind` 只保留一个，Spring Bean 优先于 ServiceLoader。

SPI 分两层，数据与机制分开：

- **厂商定义 / 能力**（`spring-support-datasearch-starter`）：`ProviderLimitProvider`（限制登记项）与 `ProviderModelCatalogProvider`（模型目录），都按 `META-INF/services` 装载，调用方只给「平台 + 地址」；内置实现是登记表与 models.dev 快照，新增来源（厂商控制台、私有登记表）只需加一个实现类 + 一行登记，不改 ai-starter；
- **获取机制**（`spring-support-ai-starter`）：`ProviderLimitProvider`（manual / doc / header）决定「怎么拿到数值」，`order()` 排序，与余额的 `CreditQueryProvider` 同构。

**模型信息口径**（公开目录）：快照 `provider-catalog/models-dev.json.gz`（187 家 / 7568 个模型，约 0.42 MB）随 datasearch 发布，字段映射如下：

| 目录字段 | 落点 | 说明 |
| --- | --- | --- |
| `description` | `sys_ai_provider_model.description` | 只在为空时补；上游 / 手写文案优先 |
| `cost.input` / `cost.output` / `cost.cache_read` / `cost.cache_write` | `sys_ai_model_metrics.price_input_per_musd` 等 | USD / 百万 token；已有价格不覆盖，手动锁定字段跳过 |
| `limit.context` / `limit.output` | 模型行 `context_window` / `max_tokens` + 指标同名列 | token 数；只补空值 |
| `modalities` / `tool_call` / `reasoning` / `attachment` / `structured_output` / `temperature` / `open_weights` | 模型行能力位 + `metrics` | 只补空值；`null` 表示目录没写，不当成 `false` |
| `knowledge` / `release_date` / `last_updated` | 模型行同名列 | 只补空值 |
| `streaming` / `async` | — | **models.dev 没有这两个字段**，接口返回 `null`，页面显示「未收录」；不按协议默认成「支持」 |

**已核对口径的条目**（只有这些带数值 / 计费口径，其余条目只有文档入口）：

| 厂商 | 名称 | 核对程度 | 官方文档 |
| --- | --- | --- | --- |
| `deepseek` | DeepSeek | 已核对（含数值） | `api-docs.deepseek.com/quick_start/rate_limit` |
| `moss` | Moss | 已核对（仅口径） | `platform.moss.cn/docs/errors-and-limits/limits` |

登记表由 datasearch 的 `provider-catalog/provider-limit-docs.json` 提供，后端 `ProviderLimitProvider` SPI 与本文档共用这一份数据；其余 188 家只有官方文档入口（models.dev 目录的 `doc` 字段，多为模型/接口文档而非限制页），没有数值口径，页面不替厂商编数字。

DeepSeek 的并发是账号级（所有 API Key 合并计算），官方按模型给固定值；Moss 只公布了计费口径与「以服务端错误码为准」，没有固定并发 / RPM 数字；OpenAI / Anthropic / Gemini 是按账户等级分级，本表不写死数字，运行时交给响应头观测。

**为什么 200+ 家都能覆盖**：网关类的限流头是行业通行做法，只要能拉到 `/models` 就能顺带读到；读不到就说明对方没有公开口径，页面照实说「未收录」，不编数字。中转站 / 自建网关也可以把后台看到的并发、RPM 填进 `extra.limits_manual`，同步时原样落库。

## 七、已知缺口

- **Anthropic 官方拉模型缺 `anthropic-version`**：`requestUpstreamModels` 只发一个认证头，官方 `/v1/models` 除 `x-api-key` 外还要 `anthropic-version: 2023-06-01`，所以 `anthropic` 模板用官方 Key 拉模型会 401（「检测协议」那条链带了这个头，能过）。目前只能靠 CC 中转站或手填模型；要让官方 Key 直接可拉，得在拉模型链路补上这个头。
- 有官方余额接口、但本仓库还没有预设的厂商（如智谱、MiniMax 等）：没有拿到官方文档原文，一律不加，避免编地址；这类暂时落到「中转探测」，不通再用手配的「自定义地址 + 字段表达式」；
- 每家的余额字段路径没有统一的行业标准，同一个 `billing` 口径在不同站点也会返回不同单位（USD / 美分 / 次数），表达式兜底就是为这个准备的。
- **免费渠道**是纯路由聚合（模型来自运行时合并路由表），自己没有账户，模板里的 `free.nomifun.com/v1` 只是占位地址；余额面板仍会按「中转探测」去请求它，结果没有业务意义，看这一行时忽略余额列即可。
- **限制只能观测到「上游肯说」的那部分**：限流做在网关 / nginx 层、响应头不返 `*ratelimit*` 的站点，这次同步拿到的就是「未收录」，只能靠 `extra.limits_manual` 手填；登记表 205 家里只有 2 家核对过口径（DeepSeek 并发、Moss 计费），其余 188 家只有文档入口，没有数值，不编数字。
- **流式 / 异步没有公开来源**：models.dev 不提供这两个字段，OpenAI 兼容协议本身也都支持 `stream`，但「模型 / 厂商是否真的支持」属于商用能力声明，没有目录可依；接口返回 `null`、页面写「未收录」，要判断得看厂商文档或实际调用。
- **价格是 models.dev 的目录价**（USD / 百万 token），不是中转站的实际结算价；渠道价请以上游 `/models` 或手工录入为准，公开目录只做补位，已有价格不覆盖。
- **目录快照随包发布**：`provider-catalog/models-dev.json.gz` 生成于 2026-11-16，不会自动联网刷新；新增厂商 / 模型要重跑 `pages/ai/docs/gen-model-snapshot.js`（联网拉 models.dev 并裁剪）并重新发版。
- **限制落库后不参与限流**：`ProviderThrottle` 读的是 `extra.max_concurrency` / `extra.requests_per_minute`（供应商表单的两个字段），不读 `extra.provider_limits` 或 `limits_manual`；同步到的官方并发 / RPM 目前只做展示，要让它生效得再拉一条「限制 → 闸门」的读取链。
- **`extra.limits_manual` 目前没有独立表单**：写入口是供应商的 `extra` 配置（接口 / 库），管理面还没有「并发 / RPM / 配额」的输入控件；要改只能改 `extra`。这一步没做，是因为先要把同步链路跑通。
- **上游 pricing 不是每家都有**：中转站 `/models` 大多只回 id 与 name，`pricing` 只有 OpenRouter 这类聚合站才带；没有上游价格时计费标准只能来自官方指标源（`ChatClientIndicators`），两条都没有就显示「未接入」，不猜价格。
