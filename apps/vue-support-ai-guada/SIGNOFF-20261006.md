## 2. 本轮修复（交付内容）

### 2.1 SSE 空帧（`workspace/events`）

- **症状**：`GET /workspace/events` 返回的 SSE 帧只剩空 `data:`（curl 实测 14 字节、
  两个空帧），事件体丢失。
- **根因**：`BinaryHttpMessageConverter`（spring-support-common-starter）在
  `mediaType=null` 时 `canWrite` 短路认领所有类型；`writeInternal` 在守护线程里
  没有 ThreadLocal `HttpServletRequest`，写出 0 字节。
- **修法**：`AiWorkspaceEventStreamService` 改为自序列化 —— `objectMapper.writeValueAsBytes(payload)`
  后 `.data(byte[])`，并构造注入 `ObjectMapper`；与既有
  `NginxMetricStreamRegistry#sendJson` 同口径。
- **验证**：`api-accept` SSE 段 4 项 PASS（收到真 `add` 事件 JSON 载荷、path 相对根、
  sessionId 原样回传、15s 心跳）。

### 2.2 Agents 包管理 404

  multipart/JSON 双映射；`resolveUserPackage` 防路径穿越；
  `publishAgentsRoot()` 回写 `nomifun.agents-root`。
- 市场端点实为 `/api/agents/packages/market/sources|search`。
- **验证**：`api-accept` agents 段 21 项 PASS；sweep `[Agents] 45 可点 / 0 异常`。

### 2.6 视觉管线配置区读写 404（`/capabilities/:pipeline`）

- **症状**：`/capabilities/ocr` 加载期出现 `404 GET /v2/global-settings/ocr`（全站 sweep 唯一 4xx），
  配置区一张表单项都不渲染，点「保存配置」同样打到不存在的路径 → **读与写双双失效**。
- **根因**：前端 `pipelineApi.config/updateConfig` 指向 `/v2/global-settings/{group}`，
  但后端 `/v2/global-settings` **只有无参的 `GET/PUT`**（单条记录接口）；按分组的真实出口是
  `GET/PUT /v2/settings/{group}`（`SettingsController`）。且该出口是**双层信封**
  `{code, data:{success, data:{field -> value}}}`，`javaApi.ts` 的客户端 `unwrap:false`，
  直接取 `res.data` 只会拿到内层信封。
- **修法**：
  - `javaApi.ts` 新增 `flattenGroupSettings()`，`pipelineApi.config/updateConfig` 与
    `settingsApi.globalBeans/updateGlobalBeans` 全部改指 `/settings/{group}` 并就地摊平，
    形状与 `settings.api.ts` 的 `fetchGroupSettings` 一致；
  - `CapabilityPage.vue` 新增 `configGroup` ref，取管线自述的 `configGroup`
    （如文生图管线 → `generate` 组，此前拿路由里的 pipeline code 当分组名，二次出错），
    并过滤 `__meta`（每项的 origin/overridden 归属信息，不是可编辑字段）。
- **验证**（浏览器 + 接口真值往返）：
  - `/capabilities/ocr` 配置区渲染出 **7 个字段** = API 返回 8 键 − `__meta`；日志中
    `/v2/global-settings/ocr` 最后一次 404 停在改动前的 `03:07:16`，此后再无该请求；
  - 点「保存配置」→ toast「配置保存成功」→ 接口读回 `sort_reading_order=false`（真写入生效）；
  - 随后按原值还原：`detector_model=""`、`sort_reading_order=true`、
    `device=cpu`、`detector_threshold=0.5`、三个 model 字段为空，与改动前完全一致。

### 2.9 生产级 sweep 实测出的缺陷：全站弹窗按 Esc 关不掉（`LDialog.vue`）

- **现象**：点开任意弹窗后直接按 `Esc`，弹窗纹丝不动。实测（dist 生产形态）：
  打开技能详情弹窗 → `activeElement` = `BODY` → `keyboard.press('Escape')`
  → 遮罩计数仍为 `3`，**没有关掉**。
- **根因**：`LDialog` 把 `@keydown.esc` 绑在 overlay 根节点上（模板 127 行），
  overlay 虽带 `tabindex="-1"` 但**从不主动获焦**。用户用鼠标点按钮打开弹窗后
  焦点仍停在 `body`，按键事件根本不经过 overlay，handler 收不到 —— Esc 天然无效。
  只有焦点恰好落在弹窗内部（Tab 进入、或点过弹窗内可聚焦元素）才关得掉。
- **影响面**：`<LDialog>` 被全站 **41 处**弹窗复用，等价于「全站弹窗 Esc 均不可用」。
- **修法（不碰 focus，避免回归）**：新增模块级 Esc 栈 + document 级监听，
  只在有弹窗打开期间存在、且**只关最上层**那个。
  - 之所以用栈而非每实例各监听一条 `document`：存在「弹窗里再开弹窗」，
    每实例都监听的话一次 Esc 会把整叠全关掉。
  - 焦点在最上层弹窗**内部**时必须让开（此时 overlay 自己的 `@keydown.esc` 已处理，
    document 监听随后也会收到冒泡，两边都执行就 `close()` 两遍 →
    `update:modelValue`/`close`/`closed` 重复 emit、定时器叠加）。
  - **刻意不做**「打开时聚焦 overlay」：会抢走弹窗内输入框由业务代码自行调用的 `focus()`，
    属行为回归；本仓 `src` 内 `autofocus` 用法为 0，但业务手动 focus 仍存在风险。
  - `onBeforeUnmount` 里摘登记项，避免组件被父级 `v-if` 直接卸载时栈里留死记录。
- **验证**：`probe-esc.cjs` 对 dist 生产形态 **3/3 PASS、0 pageError**：
  ① 焦点在 body 时按 Esc → 遮罩 `3→0`；② 焦点在 overlay 内时按 Esc → `3→0`（且不重复 close）；
  ③ 点 X 关闭按钮仍可用（回归）。

### 2.10 生产级 sweep 实测出的缺陷：出图媒体**同图重复派发 159×**（`authImage.ts`）

这条是 `sweep-final3` 上 **10 条 FAIL 的唯一根因**，也是本轮最重要的功能修复。

- **现象**：`/image-generate` 静置 15 秒（**一个按钮都不点**）：
  | 指标 | 修复前 | 修复后 |
  |---|---|---|
  | 总请求 | **3182** | **20** |
  | 不同地址 | 20 | 20 |
  | 平均重复倍数 | **159.1×** | **1.0×** |
  | 单地址最多请求 | **372 次** | **1 次** |
  | `net::ERR_INSUFFICIENT_RESOURCES` | **294** | **0** |
- **根因**：`authImage.ts` 的 `resolve(url)` 用 `settled.has(url)` 去重，但
  `settled.add(raw)` 写在 `load()` 的 `finally` 里 —— **要等 fetch 落地才标记**。
  而 `resolve()` 是模板里直接调用的（`ImageGeneratePage.mediaSrc(url)`），
  **每渲染一行就调一次**；地址未就绪期间页面只要重新渲染，`settled` 还是空的，
  于是再 `void load(url)` 一次，请求还没回来就又被复制。
- **为什么算 FAIL**：并发风暴打出 294 个 `ERR_INSUFFICIENT_RESOURCES`，
  被 harness 记进 `bucket.failed` → 命中元素的 `rec.err` →
  `ImageGenerate` **9 个按钮被判 `click-error` FAIL**，
  另有 1 个**已经成功跳转**（`urlChanged=true, afterUrl=/image-search`）的侧栏项
  「以图搜图」被同一串后台媒体失败拖成 FAIL。`clickErr` 全为 `null`
  —— 即**点击本身完全正常**，错在归因到的后台请求。
- **修法**：在 `resolve()` 里**派发前同步占位**（`settled.add(url)` 提到 `void load(url)` 之前）。
  语义与原意完全一致（一次地址只发一次、成功写 `blobUrls`、失败停在 `settled` 不重试 ——
  与 `load()` 内注释「避免渲染期疯狂重试」的原意相符），只是把「pending 窗口内重复派发」堵死。
  该工具被 `ImageGeneratePage` / `ImageSearchPage` / `ImageLibraryPanel` **三处共用**，一处修复全站生效。
- **验证**：`probe-media2.cjs` 同口径前后对照（上表）；`vue-tsc --noEmit` = **0 error**；
  修复随 `47c04fde` dist 重建后，`sweep-final4` 的 `[Chat]` 路由由
  `异常 1 -> 以图搜图(click-error)` 变为 **`异常 0`**。

### 2.11 验收 harness 自身的两处加固（判据只加强）

- **`before` / `forced` / `clickErr` 诊断字段**（只增不改分类）：
  原 `rec.err = rec.err || clickErr` 在 `rec.err` 已被 `bucket.failed` 占掉时，
  会把**真正的点击异常**整个吞掉，报文里只剩一串与点击原因无关的媒体请求失败 ——
  无从判断是「点不动」还是「点到了但后台请求失败」。现在 `clickErr` 单独落一份。
- **`requestfailed` 带上 `errorText`**：原只记 `GET /url`，看不出失败是连接被拒、
  资源耗尽还是别的；而这条记录会直接把当前被点的按钮判成 FAIL，
  不写清原因就无法归因。正是靠这条才发现 294 个 `ERR_INSUFFICIENT_RESOURCES`
  （而非此前误猜的 CORS / 404 / 代理 502），从而定位到 §2.10 的真根因。

### 2.12 覆盖面加强：50 个「无 accessible name」的可点控件原来根本没测

这条直接对应「**每个**可点按钮/图标都要测」—— 原判据在这 50 个上是空的。

- **原判据**：`if (!it.name) { rec.state='no-accessible-name'; warn++; continue; }`
  —— 采到了、也判定它可见可点，但**直接跳过不点**。
- **为什么这是真缺口**：这类元素在不少页面是该控件**唯一**的采集代表。
  `CLICKABLE_SEL` 只收 `button / [role="button"] / .el-button / .re-button / .rs-btn /
  a[href] / .el-dropdown-menu__item / [class*=icon-btn]` ——
  `label.el-switch` 和 `<input>` 都不在里面；`<input>` 也不在第二遍的
  `div,span,li,td,th,label,img,svg` 启发式里。于是：
  - **Element Plus 开关**只以内部 `span.el-switch__core` 被收进来（`extra:true`），
    又因为开关的表单文字在**兄弟节点**上、不在 core 的 `textContent` 里 → 无名 → 跳过；
  - **下拉/输入**只以 `div.el-input …cursor-pointer` 外层被收进来 → 同样跳过。
- **实测规模（`sweep-final4`）**：`no-accessible-name=50`
  （`el-switch__core` 14 个：SystemSettings 9 / DefaultModels 1 / Agents 4；
  `el-input…cursor-pointer` 36 个，全在 DefaultModels），**全部 `extra:true`、全部未点击**。
  同一分类下 Bots 的 `el-switch__core` 因旁边恰好有文字拿到 name、`state=ok` ——
  说明这类元素**点得动、也测得出来**，跳过纯属误伤。
- **改法（只加强不放松）**：删掉 `continue`，改为 `rec.noName = true` 后**照常走点击与分类**；
  无障碍观察改由 `summary.noAccessibleName` 按 `noName` 标记统计，并在汇总里**单独打印一行**
  （「可点但无 accessible name（已照常点击，仅无障碍观察，不计 FAIL）」），
  即 a11y 问题**不会因为点了它就被抹掉**，只是不再以「不测」来体现。
- **验证**：`SystemSettings` 单路由复验 —— 9 个 `el-switch__core` 全部进入
  「无可访问名的可点元素」清单 **且全部被点击**，其中一条 `effect`
  为 `接口1次 toast1 弹窗0 DOM变更25条`（开关真的切了）。
  ⚠ 该次复验的 21 条 `click-error` 落在后端换包启动期的 502 窗口内（见 §1 环境事故 ③），
  **属环境停机、不作为判据结论**。

### 2.13 一条 500 的定性：`POST /api/knowledge/bases/{id}/ask`（**非按钮缺陷**）

`sweep-final4` 的 `state-dependent` 告警里带了一条 `5xx:500 .../ask`，逐层查证如下：

- **前端报文没问题**：`KBAskPanel` 走 `askKnowledgeBase(kbId, text, 6)`
  → `POST /api/knowledge/bases/{id}/ask`，body `{query, top_k:6}`。
  用**完全相同**的报文直连后端（`probe-ask-empty.mjs`）：
  | 场景 | 结果 |
  |---|---|
  | 空知识库（0 文档）提问 | **200**，正常返回 answer + `citations:[]` + `elapsed_ms` |
  | 不存在的 kbId | **404** `NOT_FOUND 知识库不存在` |
  | 缺 `query` / `query` 为空串 | **400** `INVALID_PARAM query 不能为空` |
  三条对照说明：**参数与路径处理都对，空库也走通了 LLM 降级作答**，
  500 不是「空库没数据」这个最常见的形态。
- **当时那个库已不存在**：出事的 kbId `01a115a4-…` 在 run 之后随环境清理一起消失
  （`GET /api/knowledge/bases` 从 1 条变 0 条），无法复打当时状态；
  500 的具体诱因（该库的向量索引/根目录被摘、或当次 LLM 上游抖动）**无法回溯**。
- **结论**：该条记为 **`state-dependent` WARN（非 FAIL）**，点击本身产生了可观测效果
  （`接口1次 / DOM变更9条`），**前端与按钮无缺陷**；
  后端在该状态下回裸 500（而非像 404/400 那样给类型化错误）属**健壮性观察项**，
  需改 jar 才能修，而 jar 当前由他人会话每小时级换包，不在本轮交付范围内。
- **探针自清**：验证用的临时库 `zz-sweep-probe-tmp` 在 `finally` 里 `DELETE` 掉了，
  复核清理后列表为 `[]`，**未往共享环境留垃圾，也未做任何批量删除**。
