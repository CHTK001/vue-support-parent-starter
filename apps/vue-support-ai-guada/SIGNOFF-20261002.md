## 2. 本次相对上一颗包改了什么（可核对的证明）

是 **09-30 13:58** 安装的旧物 —— 该模块随后还有两次提交（`375920128` shellTool 装配、
`52cb5f019` 原生工具流式降级兜底改挂响应式链），**都没进过包**。原因是 fat jar 构建

**为什么没有整体重构建**：整构建会连带改变 7 个条目，其中包含
`BOOT-INF/classes/db/init/V1.0__init_all_ai.sql`（+906 B，**DDL**）与
`BOOT-INF/classes/ai-starter.yml`（配置），以及另外 4 个模块 —— 那会触到
「不要改数据库」的红线，且裹入未经本范围验收的改动。

**实际做法（外科式替换）**：只把新构建的那个模块 jar 换进原包，其余逐字节保留。
条目清单对比（1433 条 vs 1433 条）：

```
only in new = 0   only in live = 0   size differs = 1
  ~ BOOT-INF/lib/utils-support-deeplearning-agentscope-starter-4.0.0.42.jar
      live=61511  new=61698
```

即：**相对上一颗包，只有 agentscope 模块这一个条目变了**；DDL、配置及其余 1431 个
条目全部等长不变。替换前经 `jar-guard.sh` 校验（`OK 条目数=1433`）。

## 8. 本轮验收暴露的两类抖动（都不是产品回归，已分别处置）

1. **冷启动时序**：应用刚重启后立刻跑，`prod-accept` 超 300s 预算、`records-accept`
   的「已用时每秒递增」失败；等应用预热后复跑即 31/0、20/0。
2. **上游延迟**：`media-store-accept` 用 `agnes-image-2.5-flash` 且等待预算短于上游
   实际延迟（实测同刻 2.0 用 60s、2.5 用 18s，波动大），报「task never reached
   terminal」；上游快时复跑即 6/0。已用直连探针证明该模型本身可 SUCCESS。

同时修掉 `video-card-acc` 自身的三处测试脆弱（均属测试问题，非产品缺陷）：
逐键录入丢末位字符（改 `insertText`）、参数弹层未收起吞掉 Enter（提交前先关闭，
并把发送按钮限定到当前 composer）、`is-loaded` 标记采样早于 `loadeddata`（改为等待）。
