### 3b. 有界负载 / 稳态（`ai-load-acceptance`）

目标是与他人共用的生产实例，故**刻意压低并发与时长**；它不是长时间浸透。

- 读阶段 6 worker × 12 轮 × 3 端点 = **216 请求**；**5xx=0、网络错误=0**。
- 写阶段：负载期间提交真实图像生成，**SUCCESS 并带回 url**。
- 负载后后端仍正常应答（登录 200）。

断言写的是「**成功**」而不是「有终态」——FAILED 也是终态，用后者会让坏上游静默通过。

### 6b. `generate-acc` 的数据前提（本轮踩到并已解决）

`generate-acc` 第 1 步就要求 `/image-generate` 页面已有**成功的**历史卡片
（`page.waitForSelector('.wg-card:not(.is-skeleton)')` + `head.thumbs > 0`），
而 `records-accept` / `id-stability-accept` 内含「全部删除 / clear leftovers」会清空图库
→ 顺序执行时它会因**无数据**而超时（**不是产品缺陷**）。

解决（本轮采用，作为复跑前置）：用 mock 种入若干**成功图像**：

```bash
curl -s -X POST -H 'Content-Type: application/json' -H "Authorization: Bearer $TOK" \
  -d '{"type":"image","model":"acc-image-probe","prompt":"seed","size":"1280x720","count":1}' \
  http://127.0.0.1:8787/v2/ai/generate/tasks
```

**注意**：`size` 与 `count` 是必填；缺失时返回 `S0512C0000 系统处理异常` 并留下一条**卡在 PENDING** 的行，
而应用「同时只允许一个生成」的约束会被该行**阻塞**后续提交（需 cancel+delete 清掉）。
按项目要求，**这些测试数据保留，不清理**。

## 8. 本轮验收暴露的抖动与教训（都不是产品回归）

1. **产物绑定不够，必须同时绑「服务连续性」。**
   上一版编排只绑 jar md5。并发会话用 `systemctl restart`（**手动重启不增加 `NRestarts`**）
   在验收中途重启后端，jar 未变 → 门没响，但 `settings-acc` 撞上 `ECONNREFUSED` 假红。
   现编排改为 **md5 + MainPID + ExecMainStartTimestamp** 三重绑定，任一变化即判 **VOID**。
2. **前端必须单实例，且不能静默换端口。**
   项目自带的 `vite-once.cmd`（`--strictPort`）已占 15689；我的编排又起了一个，
   因 vite 默认「端口忙就 +1」被挤到 15690，套件仍打 15689 → 页面状态错乱。
   现改为**复用**已监听的 15689，不再重复启动。
3. **`generate-acc` 有数据前提**（见 §6b）。
4. **冷启动时序**：应用刚重启后立刻跑，个别套件会超预算；预热后通过。
5. **上游延迟**：`media-store-accept` 用 `agnes-image-2.5-flash`，上游延迟波动大；上游快时通过。
